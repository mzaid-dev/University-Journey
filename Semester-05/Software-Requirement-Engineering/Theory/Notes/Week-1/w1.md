# **Topic 3: Project Management Challenges**

Week 1 — Page 5

Your teacher identifies five major challenges.

### **1. Scope Creep**

When project requirements grow beyond the original agreement without adjustments to time, budget, or resources.

Example: Initially, a university application requires five features. Later, the client keeps requesting additional features without changing the deadline or budget.

### **2. Budget Overruns**

When a project spends more money than originally planned.

Example: The project was planned for Rs. 500,000 but eventually costs Rs. 700,000.

### **3. Resource Constraints**

When sufficient materials, funding, or skilled team members are not available.

Example: A software project does not have enough developers.

### **4. Delays**

When tasks take longer than scheduled, pushing back deadlines and final delivery.

Example: A project scheduled for three months takes five months.

### **5. Poor Communication**

When information is not properly shared among team members and stakeholders, causing confusion and mistakes.

Example: The client changes a requirement, but the development team is not informed.

### **Important comparison**

| Challenge            | Main meaning                       |
| -------------------- | ---------------------------------- |
| Scope Creep          | Requirements keep growing          |
| Budget Overruns      | Money exceeds the plan             |
| Resource Constraints | Resources are insufficient         |
| Delays               | Work takes longer                  |
| Poor Communication   | Information is not shared properly |

# **Topic 4: Software Error, Fault and Failure**

Week 1 — Pages 6–7

Very important for conceptual questions

This is one of the concepts you must understand properly.

There are three different terms:

- Error
- Fault (Bug/Defect)
- Failure

[medium.com](https://medium.com/qualitynexus/where-bugs-are-really-born-the-truth-behind-errors-defects-and-failures-9282a22cdab2?utm_source=chatgpt.com)

### **1. Error**

An error is a human mistake made by a developer, designer, or tester during software development.

Example: A developer mistakenly writes:

```
if (age < 18)
```

instead of:

```
if (age <= 18)
```

### **2. Fault (Bug/Defect)**

A fault is the physical manifestation of a human mistake in software code or design documents.

Example: The incorrect conditional logic remains in the source code.

### **3. Failure**

A failure is an observable event where running software deviates from its expected behavior.

Example: When the application runs, it produces an incorrect result.

### **Understand the relationship**

**ERROR**

Human makes a mistake

**FAULT**

Mistake exists in the code

**FAILURE**

Software behaves incorrectly when executed

**Golden exam point:**

An error is a human mistake, a fault is the defect introduced into the software, and a failure is the observable incorrect behavior during execution.

### **Difference table**

| Error                 | Fault              | Failure                   |
| --------------------- | ------------------ | ------------------------- |
| Human mistake         | Code defect        | Incorrect behavior        |
| Created by a person   | Exists in software | Observed during execution |
| Example: Wrong typing | Wrong code         | Application crashes       |

Remember: A fault does not necessarily produce a failure every time. The faulty code must be executed under conditions that trigger it.

# **Topic 8: Software Requirements**

Week 1 — Page 13

Extremely important definition

Your slides provide several definitions from different sources.

Let's understand the main idea first.

**Software requirements describe what a software system must do or what conditions it must satisfy to address stakeholder needs.**

### **Definitions mentioned in your slides**

**1. Larman (2002)**

A capability that the system must deliver or a condition that it must satisfy in order to address a need of a stakeholder.

**2. SEBOK Chapter 2**

The Software Requirements Knowledge Area is concerned with:

- Elicitation
- Analysis
- Specification
- Validation

**3. IEEE Std 729**

A condition or capability that must be met or possessed by a system to satisfy a contract, standard, specification, or other formally imposed document.

### **Two important points**

Your teacher also explains:

1. Software requirements are a complete specification of the desired external behavior of the software system to be built.
2. Software requirements describe **what** the software will do without describing **how** it will do it.

**Example:**

Requirement:

"The system shall allow students to log in using their university credentials."

This tells us WHAT the software must do.

It does not explain HOW the developer will implement the login functionality.

# **Topic 9: Requirements Engineering vs Software Requirements Engineering**

Week 1 — Page 14

This is a possible short or long question.

### **Requirements Engineering (RE)**

According to DoD (1991), Requirements Engineering involves lifecycle activities devoted to:

1. Identification of user requirements.
2. Analysis of requirements to derive additional requirements.
3. Documentation of requirements as a specification.
4. Validation of documented requirements against user needs.
5. Supporting processes for these activities.

### **Software Requirements Engineering**

According to Thayer et al. (1997):

Software Requirements Engineering is the science and discipline concerned with establishing and documenting software requirements.

### **Difference**

| Requirements Engineering                                                                         | Software Requirements Engineering                              |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| Covers lifecycle activities for identifying, analyzing, documenting and validating requirements. | Focuses on establishing and documenting software requirements. |

**Remember the authors:**

- DoD (1991) → Requirements Engineering.
- Thayer et al. (1997) → Software Requirements Engineering.

# **Topic 11: Types of Requirements**

Week 1 — Pages 16–17

Your lecture introduces two main types:

# **FR**

**Functional Requirements**

Describe system services or functions.

What does the system do?

# **NFR**

**Non-Functional Requirements**

Describe constraints on the system or development process.

How well does it work?

### **Functional Requirements (FR)**

Describe the functions or services that the software must provide.

Examples:

- User login.
- Register a new account.
- Search for products.
- Submit an assignment.
- Generate a report.

### **Non-Functional Requirements (NFR)**

Describe constraints or quality expectations of the software or its development process.

Examples:

- System response time.
- Security.
- Reliability.
- Usability.
- Performance.

### **Most important difference**

| Functional            | Non-Functional            |
| --------------------- | ------------------------- |
| What the system does  | How well the system works |
| Features and services | Constraints and qualities |
| Login                 | Response within 2 seconds |
| Submit assignment     | Secure data transmission  |

**Exam trick:** A question mentioning an action or feature usually indicates FR. A question mentioning performance, security, reliability or quality usually indicates NFR.

# **Topic 18: Characteristics of a Good Requirement**

Week 1 — Pages 29–30

High-priority exam topic

Your teacher provides nine characteristics.

Learn all nine. They are excellent material for MCQs, short questions, and scenario-based questions.

## **First five characteristics**

### **1. Feasible**

A requirement is feasible if it can be accomplished using available resources, budget, skills, schedule, and technology.

Example: A university can develop a student portal within its available budget and resources.

### **2. Valid**

A requirement is valid if it is something the system must meet.

Example: Student login is a necessary requirement for a student portal.

### **3. Unambiguous**

A requirement is unambiguous if it has only one interpretation.

Example:

Ambiguous: "The system should respond quickly."

Clear: "The system shall respond within 2 seconds."

### **4. Verifiable**

A requirement is verifiable if the finished system can be tested to ensure it meets the requirement.

Example: Test whether the system responds within 2 seconds.

### **5. Modifiable**

A requirements specification is modifiable if changes can be made easily, completely, and consistently while maintaining its structure and style.

Example: A developer can update a requirement without rewriting the entire document.

## **Remaining four characteristics**

### **6. Consistent**

A requirement is consistent if it does not contradict other requirements, corporate documents, or standards.

Example: One requirement says the system allows access to students, while another says only teachers can access it. These conflict if they concern the same function.

### **7. Complete**

A requirements specification is complete if it includes all relevant and correct requirements and sufficient information is available to build the product.

Example: A login requirement specifies the necessary inputs and expected behavior.

### **8. Traceable**

A requirement is traceable if its source, implementing product components, and related test cases can be identified.

Example: We can identify:

- Who requested the login feature.
- Which component implements it.
- Which test case verifies it.

### **9. Concise**

A requirements specification is concise if removing any requirement changes the definition of the product or system.

Example: Requirements contain necessary information without unnecessary content.

## **Complete revision table**

| Characteristic | Remember this meaning                         |
| -------------- | --------------------------------------------- |
| Feasible       | Can be achieved                               |
| Valid          | Must be satisfied                             |
| Unambiguous    | One interpretation                            |
| Verifiable     | Can be tested                                 |
| Modifiable     | Easy to change                                |
| Consistent     | No contradictions                             |
| Complete       | All necessary information                     |
| Traceable      | Source, implementation and tests identifiable |
| Concise        | No unnecessary requirements                   |

**Professor's advice:** Learn the exact meaning of each word. Your examiner can give you a situation and ask which characteristic is being violated.

# **Topic 19: Example of an Ambiguous Requirement**

Week 1 — Page 31

This is an excellent scenario-based question.

Consider this requirement:

"The system should support large files."

What is wrong with it?

The word "large" is unclear.

There are two possible interpretations.

**Interpretation 1: Large File Size**

The application should allow users to upload files up to 10 GB.

Focus:

- Storage.
- Upload limits.
- Transfer performance.

**Interpretation 2: Large Number of Files**

The system should efficiently manage millions of files.

Focus:

- Scalability.
- Indexing.
- Search performance.

### **Why is this a problem?**

Both development teams may understand the same requirement differently and build different features.

### **How to solve it?**

Rewrite the requirement with measurable and clear information.

For example:

"The system shall allow users to upload individual files up to 10 GB."

Now there is only one clear interpretation.

**Exam-ready answer:**

An ambiguous requirement is a requirement that has multiple interpretations. It creates confusion because different stakeholders or developers may understand it differently, resulting in incorrect implementation.
