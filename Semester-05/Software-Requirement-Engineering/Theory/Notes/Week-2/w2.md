# **PART 1 – Types of Requirements**

## **1. What are Requirements?**

A requirement describes what a system must do or what condition it must satisfy.

**Simple definition for exams:**

A software requirement is a feature, function, or condition that a software system must satisfy to meet user needs.

### **Example: University Management System**

Imagine we are developing a university management system.

The university wants:

- Students to log in.
- Students to view their GPA.
- Teachers to upload marks.
- The system to respond quickly.
- Student information to remain secure.

All these are requirements of the system.

**Remember:** Requirements explain what the system needs to provide, not necessarily how developers will build it.

## **3. Functional Requirements (Very Important)**

High-priority exam topic

### **Definition**

A functional requirement defines the functions or services that a system must provide.

In simple words:

**It describes WHAT the system should do.**

It explains:

- What inputs the system should accept.
- What outputs the system should produce.
- What data the system should store.
- What calculations the system should perform.
- What actions the system should support.

### **Example 1: University Management System**

- The system shall allow students to log in.
- The system shall allow students to view their GPA.
- The system shall allow teachers to upload marks.
- The system shall generate student result reports.

All these are functional requirements because they describe system actions.

### **Example 2: Library Management System**

Your slide on page 5 gives these examples:

1. The system shall allow users to search books by title, author, or ISBN.
2. The system shall allow students to issue available books online.
3. The system shall record book returns and update availability.
4. The system shall send overdue alerts to students.

### **Example 3: ATM System**

According to page 6:

- Authenticate the customer using a card and PIN.
- Display the account balance.
- Dispense cash for a valid withdrawal request.
- Allow fund transfers.
- Print a transaction receipt.

### **Exam-ready answer**

**Functional Requirements:** Functional requirements define the functions and services that a system must provide. They describe what the system should do, including inputs, outputs, data handling, and calculations.

## **4. Non-Functional Requirements (Very Important)**

### **Definition**

A non-functional requirement defines the quality, performance, and constraints of a software system.

In simple words:

**It describes HOW WELL the system should work.**

Examples include:

1. Performance
2. Reliability
3. Security
4. Usability
5. Scalability

### **Example: Food Delivery Application**

Your slide on page 8 gives examples:

| Quality     | Requirement                                             |
| ----------- | ------------------------------------------------------- |
| Performance | App homepage loads within 2 seconds on a 4G connection. |
| Reliability | System maintains 99.9% monthly availability.            |
| Security    | Payment data is encrypted during transmission.          |
| Usability   | A first-time user can place an order without training.  |

### **Why are Non-Functional Requirements important?**

If non-functional requirements are not met, the system may become useless, even if its functions work correctly.

For example:

An ATM may allow users to withdraw money, but if it takes 10 minutes to process a transaction, users will not be satisfied.

### **Exam-ready answer**

**Non-Functional Requirements:** Non-functional requirements define the quality attributes and constraints of a system. They describe how well the system performs, including performance, security, reliability, and usability.

## **5. Difference Between Functional and Non-Functional Requirements**

Must prepare for comparison question

| Functional Requirements             | Non-Functional Requirements                     |
| ----------------------------------- | ----------------------------------------------- |
| Describe what the system does.      | Describe how well the system works.             |
| Define system features and actions. | Define quality attributes and constraints.      |
| Focus on functionality.             | Focus on performance and quality.               |
| Example: User can log in.           | Example: Login completes within 2 seconds.      |
| Example: Search books.              | Example: Search results appear within 1 second. |
| Example: Transfer money.            | Example: Transactions must be secure.           |

**Easy trick to remember:**

- Functional = WHAT
- Non-Functional = HOW WELL

### **Let's understand with one example**

Suppose you are developing StudySync AI.

**Functional requirements**

- Student can create an account.
- Student can add assignments.
- Student can view a study plan.

**Non-functional requirements**

- The application should load within 2 seconds.
- Student data must remain secure.
- The application should be easy to use.

Notice the difference: adding an assignment is an action, while loading quickly is a quality requirement.

## **6. Domain Requirements**

### **Definition**

Domain requirements are requirements that come from the application domain and reflect its important rules and characteristics.

In simple words:

**These are rules that come from the business or industry where the software is used.**

They may come from:

- Business practices.
- Government regulations.
- Industry standards.
- Company policies.

### **Example 1: Hospital Management System**

A hospital system must follow patient-record rules.

### **Example 2: Banking System**

A banking system must follow banking regulations.

### **Example 3: Commission System**

Your slide on page 12 gives an interesting example:

In a commission-based sales business, negative commission is not allowed.

The system must follow this business rule and must not calculate negative commission.

### **Important points**

- Domain requirements come from the application domain.
- They may be functional or non-functional.
- They can impose strict restrictions on the system.
- Sometimes domain experts find it difficult to explain these requirements.
- Missing domain requirements can cause user dissatisfaction.

**Exam-ready answer:**

Domain requirements are requirements derived from the application domain, business practices, regulations, and industry standards. They describe the rules and characteristics of a particular application area.

## **7. Inverse Requirements**

### **Definition**

Inverse requirements specify what the system must NOT do.

In simple words:

**They describe restrictions on system behavior.**

### **Examples**

- The system shall not allow unauthorized users to access student records.
- The system shall not allow students to modify their examination marks.
- The system shall not allow users to withdraw more money than their available balance.

### **Understand the difference**

| Normal functional requirement | Inverse requirement                                   |
| ----------------------------- | ----------------------------------------------------- |
| Student can view marks.       | Student cannot modify marks.                          |
| User can access an account.   | Unauthorized users cannot access an account.          |
| User can withdraw money.      | User cannot withdraw more than the available balance. |

**Exam-ready answer:**

Inverse requirements specify the actions or operations that a system must not perform. They define restrictions on system behavior.

## **8. Design and Implementation Constraints**

### **Definition**

These are development guidelines or restrictions within which the designer and developer must work.

In simple words:

**They define which technologies, platforms, tools, or design choices must be used.**

### **Examples from your slide (page 17)**

1. The system shall be developed using the Microsoft .NET platform.
2. The system shall be developed using open-source tools.
3. The system shall run on the Linux operating system.

Other examples:

- The application must use Java.
- The database must be MySQL.
- The application must support a particular device platform.

### **Important points**

- They restrict design and implementation options.
- They define the technology and environment of the system.
- They may specify platforms, operating systems, programming languages, and databases.

**Exam-ready answer:**

Design and implementation constraints are restrictions that define the technology, platform, tools, and environment that developers must use while developing a system.

## **9. Commercial Constraints**

### **Definition**

Commercial constraints are business-related restrictions that affect the project plan and development methods.

In simple words:

**They define the project's budget, delivery time, and development process.**

### **Examples**

- The project must be completed within 6 months.
- The development budget must not exceed Rs. 500,000.
- The project must follow the agreed development methodology.

### **Important points**

They mainly include:

1. Development process or methodology.
2. Project cost.
3. Delivery date.
4. Development time frame.

Your teacher's slide explains that these constraints are often included in contracts or project plans.

**Exam-ready answer:**

Commercial constraints are business limitations that restrict project planning and development, including budget, development time, delivery dates, and development methods.

## **11. What is Agile?**

Agile is an approach to software development in which a project is developed in small parts, with regular feedback and improvements.

In simple words:

**Agile means developing software step by step instead of building the entire system at once.**

### **Example**

Suppose we are developing a university management system.

Instead of developing everything together:

- Sprint 1: Login system.
- Sprint 2: Course management.
- Sprint 3: Assignment management.
- Sprint 4: Result management.

After each sprint, the team can review the work and improve it.

## **12. Requirements Engineering in Agile**

In Agile, requirements are not fixed permanently at the beginning.

They are continuously reviewed and improved as new feedback arrives.

Your Week 2 slides introduce requirements engineering in Agile, especially the organization of work into epics, user stories, tasks, and smaller work items.

### **Important concept**

Agile focuses on:

- Continuous feedback.
- Customer involvement.
- Flexible requirements.
- Small development cycles.
- Continuous improvement.

## **13. Product Backlog**

Important exam topic

### **Definition**

A product backlog is a dynamic, prioritized master list of all desired features, bug fixes, technical work, and enhancements required for a product.

In simple words:

**A product backlog is a list of all the work that needs to be done in a project, arranged by priority.**

### **Example: StudySync AI**

| Priority | Backlog item             |
| -------- | ------------------------ |
| High     | Student login            |
| High     | Add assignments          |
| High     | Generate study plan      |
| Medium   | Progress dashboard       |
| Low      | Change application theme |

### **Important points**

- It is dynamic, not fixed.
- It is prioritized.
- It contains features, bugs, technical work, and improvements.
- It changes according to feedback and business needs.

**Exam-ready answer:**

A product backlog is a dynamic and prioritized list of all features, bug fixes, technical work, and improvements required for a product.

### **1. Epic**

An Epic is a large body of work that delivers significant value.

- Usually too large for one sprint.
- Broken into multiple user stories.
- Represents a major feature or initiative.

Example:

**Implement Online Payment System.**

### **2. User Story**

A User Story is a short and simple description of a feature from the end user's perspective.

It follows this format:

**User Story Format**

As a [type of user], I want [goal] so that [benefit].

**Example**

As a student, I want to pay my university fee online so that I do not need to visit the accounts office.

### **3. Task**

A Task is a specific piece of work required to complete a user story.

Example, for the online payment story:

- Design payment gateway UI.
- Integrate payment API.
- Write unit tests.
- Update the database.

### **4. Sub-task**

A Sub-task is a smaller breakdown of a task into more detailed steps.

Example, for the task "Integrate payment API":

- Create API configuration.
- Connect backend service.
- Handle payment responses.
- Add error logging.

### **Understand the hierarchy**

## **EPIC**

## **TASK**

## **SUB-TASK**

### **Difference table**

| Level      | Size       | Focus          |
| ---------- | ---------- | -------------- |
| Epic       | Very large | Business value |

Big → Smaller → Small → Smallest.

## **15. User Story and Acceptance Criteria**

These two concepts are very important because they can appear in practical questions.

### **User Story**

A user story explains:

- Who wants something?
- What do they want?
- Why do they want it?

Example:

As a student, I want to view my GPA so that I can monitor my academic performance.

### **Acceptance Criteria**

Acceptance criteria define the conditions that must be satisfied for a user story to be accepted as complete.

In simple words:

**Acceptance criteria tell us when a feature is considered successfully completed.**

Example:

User Story:

As a student, I want to pay my university fee online so that I do not need to visit the accounts office.

Acceptance Criteria:

- Student can enter payment details.
- System processes a successful payment.
- A payment ID is generated.
- Payment confirmation is emailed to the student.

Your lecture also gives the payment ID and email confirmation example on page 32.

### **Difference**

| User Story                       | Acceptance Criteria                  |
| -------------------------------- | ------------------------------------ |
| Describes the user's need.       | Describes conditions for acceptance. |
| Explains what and why.           | Explains when it is complete.        |
| Written from user's perspective. | Written as clear conditions.         |

## **18. Requirements Risks**

Your Week 2 PDF also covers requirements risks.

A requirements risk is a possible problem related to requirements that can negatively affect a software project.

The slides identify five important risks.

Prepare all five

### **1. Insufficient User Involvement**

It happens when users do not participate enough in requirements gathering and review.

**Example:** Developers create a university system without properly asking students what they need.

**Result:** The final system may not meet actual user needs. Late changes can also cause rework and delays.

### **2. Inaccurate Planning**

It happens when project estimates are based on unclear or incomplete requirements.

**Example:** A team estimates that a project will take two months, but missing requirements make it take four months.

**Result:** Budget overruns and project delays.

### **3. Creeping User Requirements**

It happens when requirements continue to grow during development.

It is also related to scope creep.

**Example:** Initially, the university system only needs login and GPA features. Later, users request chat, attendance, online payments, and many more features.

**Result:** Project cost and development time increase.

**How to manage it:** In Agile, new requirements can be added to the backlog and prioritized for future iterations.

### **4. Ambiguous Requirements**

It happens when a requirement is unclear and can have multiple meanings.

**Example:**

"The system should respond quickly."

What does quickly mean? One second? Five seconds?

A clearer requirement:

"The system shall respond within 2 seconds."

**Result:** Developers and testers may understand the requirement differently.

### **5. Gold Plating**

Gold plating means adding extra features or improvements that were not requested or approved by the customer.

**Example:** A customer requests a simple university login system, but developers add animations, chat, and extra features without approval.

**Result:** Extra development time, cost, and unnecessary complexity.

### **Difference between scope creep and gold plating**

| Scope Creep                                             | Gold Plating                                 |
| ------------------------------------------------------- | -------------------------------------------- |
| Requirements keep increasing beyond the original scope. | Developers add unrequested features.         |
| Often caused by changing stakeholder needs.             | Often caused by developers adding extras.    |
| Can increase project time and cost.                     | Can waste resources and increase complexity. |

**Remember all five risks:**

1. Insufficient user involvement.
2. Inaccurate planning.
3. Creeping user requirements.
4. Ambiguous requirements.
5. Gold plating.

## **20. Technical Story and Spike**

### **Technical Story**

Example from your slide (page 34):

Integrate a video player with a storage service.

### **Spike**

A Spike is a research task used to investigate a problem or find the best technical approach before development.

### **Difference**
