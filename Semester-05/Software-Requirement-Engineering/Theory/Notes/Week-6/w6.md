## **1. What is a Use Case?**

**Definition (exam-ready):**

A Use Case is a step-by-step description of how an external user or another system interacts with a software application to achieve a specific goal.

Let's understand this with an example.

Imagine a university's online registration system.

A student wants to register for a course.

[sketchboard.io](https://sketchboard.io/examples?utm_source=chatgpt.com)

The interaction is:

1. Student opens the registration system.
2. Student selects a course.
3. System checks prerequisites.
4. System registers the course.
5. System displays confirmation.

This complete interaction is a Use Case.

**Remember these three important points from your slides (page 3):**

- A use case describes interaction between an actor and a system.
- It covers the steps from the beginning to the end of a task.
- It includes actions in which the actor interacts with the computer.

### **Why do we use Use Cases?**

1. To understand user requirements.
2. To identify system functionality.
3. To understand system behavior.
4. To define project scope.
5. To help create test cases.

## **2. Key Elements of a Use Case**

This is an important topic. Your slides explain the main elements on page 5 and show them in the diagram on page 4.

There are six important elements.

# **1. Actor**

Who?

The user or external system that interacts with the software.

Example: Student, Teacher, Librarian.

# **2. Goal**

What?

The result that the actor wants to achieve.

Example: Register for a course.

# **3. Preconditions**

Before

Conditions that must be true before a use case starts.

Example: Student must be logged in.

# **4. Main Flow**

Normal steps

The normal sequence of steps when everything works correctly.

Example: Select course → Check prerequisites → Register course.

# **5. Alternative / Exception Flow**

Other paths

Different paths when something goes wrong or a condition changes.

Example: Course is full or prerequisites are missing.

# **6. Postconditions**

After

The system's state after the use case finishes.

Example: Student's course schedule is updated.

### **Understand with one complete example**

**Use Case: Student Course Registration**

| Element          | Example                                                              |
| ---------------- | -------------------------------------------------------------------- |
| Actor            | Student                                                              |
| Goal             | Register for a course                                                |
| Preconditions    | Student is logged in and eligible                                    |
| Main Flow        | Select course → Check prerequisites → Add course → Show confirmation |
| Alternative Flow | Course is full or prerequisites are missing                          |
| Postconditions   | Student's schedule is updated                                        |

Exam tip

If the exam asks you to identify the elements of a use case from a scenario, look for:

- Who is performing the action? → Actor
- What does the user want? → Goal
- What must be true before? → Preconditions
- What happens normally? → Main Flow
- What happens if something changes? → Alternative Flow
- What happens after completion? → Postconditions

## **3. Essential Use Cases vs Concrete Use Cases**

This is a very important comparison question.

Your slide 9 explains two abstraction levels.

**A. Essential Use Case**

Definition: An abstract use case that is independent of technology and user interface design.

Example:

- Customer identifies themselves.
- Customer makes a payment.

It explains WHAT the user wants, not how the interface works.

**B. Concrete Use Case**

Definition: A use case that depends on a particular technology or user interface.

Example:

- Customer inserts an ATM card.
- Customer types a PIN.

It explains HOW the interaction happens using a particular interface.

### **Difference between Essential and Concrete Use Cases**

| Essential Use Case          | Concrete Use Case               |
| --------------------------- | ------------------------------- |
| Abstract                    | Specific                        |
| Technology independent      | Technology dependent            |
| UI independent              | UI dependent                    |
| Defined at earlier stages   | Includes implementation details |
| Customer identifies herself | Customer inserts a card         |

**Easy trick to remember:**

- Essential = What?
- Concrete = How?

## **4. What is a Scenario?**

**Definition (exam-ready):**

A Scenario is a single, specific path or instance of execution through a Use Case.

Let's understand the difference.

Imagine a student wants to register for a course.

There can be three possible situations:

1. Course registration is successful.
2. Course is full.
3. Student does not meet the prerequisites.

All three situations belong to the same Use Case: Register for Course.

But each situation is a separate scenario.

**Use Case: Register for Course**

Scenario 1

**Successful Registration**

Course is available → Registration successful

Scenario 2

**Course Full**

Course is full → Registration rejected

Scenario 3

**Prerequisites Missing**

Requirements not met → Registration rejected

### **Important points from your slide 11**

- A Use Case represents all possible paths.
- A Scenario represents one specific path.
- Many scenarios can be created from one Use Case.
- Each scenario may require many test cases.

### **Difference between Use Case and Scenario**

| Use Case                            | Scenario                        |
| ----------------------------------- | ------------------------------- |
| Collection of possible paths        | One specific path               |
| Covers normal and alternative flows | Covers one particular flow      |
| Describes system interaction        | Describes a specific occurrence |
| Can have many scenarios             | Belongs to a use case           |

**Remember:** One Use Case can have multiple Scenarios.

## **5. Use Case Templates**

This topic is especially important because your teacher can give you a scenario and ask you to write a complete Use Case.

Your slides (pages 15–16) explain the template in two parts.

### **Part A: Basic information**

| Element        | Meaning                            |
| -------------- | ---------------------------------- |
| Identifier     | Unique ID of the use case          |
| Name           | Name of the user task              |
| Authors        | People who discovered the use case |
| Goal           | Expected result                    |
| Preconditions  | Conditions before starting         |
| Postconditions | System state after completion      |

### **Part B: Additional information**

| Element               | Meaning                                            |
| --------------------- | -------------------------------------------------- |
| Primary Actor         | Actor who starts the use case                      |
| Secondary Actors      | Other actors who provide services                  |
| Related Requirements  | Related functional and non-functional requirements |
| Related Use Cases     | Other connected use cases                          |
| Description of Events | Steps and scenarios                                |

### **Important: Primary vs Secondary Actor**

**Primary Actor:** The actor who initiates the use case.

Example: Student requests to borrow a book.

**Secondary Actor:** An external actor or system that provides a service during the use case.

Example: Payment Gateway processes a payment.

## **8. Relationships in Use Case Diagrams**

This is a high-priority exam topic.

There are three relationships you must understand:

1. `<<include>>`
2. `<<extend>>`
3. Generalization (Inheritance)

### **A. Include Relationship**

**Definition:**

An Include relationship represents compulsory behavior that is always required by another Use Case.

Simple meaning: One Use Case must use another Use Case.

Example: Borrow Book always requires checking book availability.

[Modeling UML Use Case Diagrams and Capturing Use Case Scenarios](https://images.openai.com/static-rsc-4/2oOJM20qEx_xMgxIk3ZqkG0esLMmFVwYqG1Fcx5GwfoF--jYo9V6fapwjdvWoFuHI8Vqre3fESc484vPaSPDezf3MzkQ1na4OwgmM-IHbD-uc4w9ppPZ-NIunFn_-RsR4r2rxcLMmO-bEedV_02jIgsik8xvjtLG2izDc5XbX4o?purpose=inline)

[vlabs.iitkgp.ac.in](https://vlabs.iitkgp.ac.in/sevl/Exp3/casestudy.html?utm_source=chatgpt.com)

**Explanation:**

- Borrow Book is the main Use Case.
- Check Availability is the included Use Case.
- Every time Borrow Book executes, Check Availability must execute.

**Remember:** Include = Mandatory / Compulsory.

### **B. Extend Relationship**

**Definition:**

An Extend relationship represents optional or conditional behavior that happens only when a specific condition is met.

Simple meaning: An additional action happens only sometimes.

Example: A student returns an overdue book. The system may require the student to pay a fine.

[PPT - Use Case Diagram : Library System PowerPoint Presentation, free download - ID:255789](https://images.openai.com/static-rsc-4/6D_uOPEUsu1iEeScRfOwwk6qpYpWW90QKXvsPB50EeCOO8Cvq0diaIOzt_osY9afst3t3wAdViK5lATwvd-HDr-IqIpNPNhYdFFnx9KrEWxaLWrs_7yKrelrbkri_SSKopw5xtyzw6yKK5sKo0vK_JRAn7Z00u_eH9YzPsVFJNE?purpose=inline)

[slideserve.com](https://www.slideserve.com/joella/use-case-diagram-library-system?utm_source=chatgpt.com)

**Explanation:**

- Return Book is the main Use Case.
- Pay Fine is an optional extension.
- Pay Fine happens only if the book is overdue.

**Remember:** Extend = Optional / Conditional.

### **C. Generalization (Inheritance)**

**Definition:**

Generalization is a relationship in which a child actor or use case inherits the common behavior of a parent actor or use case.

Example:

- Student is a type of User.
- Teacher is a type of User.

Both can share common functions such as Login and View Profile.

[Merge/Group Generalization Line - UML - Discuss the Visual Paradigm](https://images.openai.com/static-rsc-4/7letGgtq58nUWfcTMuyeu4A5lzIK16mv0LEh-Wl10ISUwU9e1eCNR14K44OGGa4c6o8f_zQlIvBRQf-1eF1CTTaDPHqjoX_PAevMn4lVmFN4k4E-5mWZmkBwD0R-nxLd5sOTpgm5rJgw5t7o9GIlxmvrkDwMh4VBegWTUgcSQyU?purpose=inline)

[forums.visual-paradigm.com](https://forums.visual-paradigm.com/t/merge-group-generalization-line/17474?utm_source=chatgpt.com)

### **Most important comparison**

| Include                         | Extend                         |
| ------------------------------- | ------------------------------ |
| Mandatory behavior              | Optional behavior              |
| Always executed                 | Executed under a condition     |
| Reuses compulsory functionality | Adds conditional functionality |
| Example: Check Availability     | Example: Pay Fine              |

Must memorize

- Include = Must happen.
- Extend = May happen.

**Important arrow direction:**

- Include: Main Use Case → Included Use Case.
- Extend: Extending Use Case → Base Use Case.

The dashed arrow points towards the included or base use case respectively.

## **12. Use Case Validation**

Your slide 6 shows four important validation points.

A good Use Case should be:

| Quality    | Meaning                          |
| ---------- | -------------------------------- |
| Complete   | All necessary steps are included |
| Consistent | No conflicting information       |
| Realistic  | Possible in the real system      |
| Testable   | Can be checked through testing   |

**Example:**

Requirement: The system should allow students to log in.

- Complete: Login steps are defined.
- Consistent: Login rules do not conflict.
- Realistic: The system can provide login functionality.
- Testable: We can test valid and invalid credentials.
