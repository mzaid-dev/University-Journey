## **2. W4H Framework (Very Important)**

Your slides introduce the W4H framework on page 2.

It is a requirements elicitation and analysis model. It helps us understand the system's scope, users, purpose, timing, and functionality.

The framework contains five questions:

# **W1**

**What?**

What should the software do or be?

# **W2**

**Why?**

Why are we building this software?

# **W3**

**Who?**

Who are the stakeholders?

# **W4**

**When?**

When are requirements developed and managed?

# **H**

**How?**

How are requirements developed and maintained?

### **Example: Password Reset System**

Your teacher gives an example on page 3.

| Question | Answer                                                      |
| -------- | ----------------------------------------------------------- |
| Who?     | Registered student                                          |
| What?    | Request a password reset link                               |
| Why?     | Incomplete features                                         |

**Understand this example:**

1. Who requests the reset? Registered student.
2. What does the student need? Password reset.
3. Why is it needed? To solve the problem of forgotten passwords.

5. How does it work? The system sends an OTP.

This is how you apply W4H to a scenario.

Exam-ready answer

**Q: What is the W4H framework?**

The W4H framework is a requirements elicitation and analysis model. It uses five questions: What, Why, Who, When, and How to understand the system's scope, purpose, stakeholders, timing, and functionality.

## **3. W1 – WHAT (Levels and Types of Requirements)**

According to page 4, requirements must be determined and agreed upon by customers, users, and suppliers before software development.

Requirements define:

1. What the software must do.
2. What the software must be.
3. What limitations exist during implementation.

Let's understand the important types.

### **A. Functional Requirements**

**Definition:** Functional requirements describe what the system must do.

They define the functions, features, inputs, outputs, and actions of the software.

Examples:

- User can log in.
- Student can submit assignments.
- Student can view results.
- Customer can withdraw money from an ATM.

**Easy way to remember:** Functional = WHAT the system does.

### **B. Non-Functional Requirements**

**Definition:** Non-functional requirements describe how well the system must perform.

They define the quality and performance of the software.

Examples:

- The system should respond within 2 seconds.
- The system should be secure.
- The system should be available 99.9% of the time.
- The application should be easy to use.

**Easy way to remember:** Non-functional = HOW WELL the system works.

### **Difference between Functional and Non-Functional Requirements**

| Functional             | Non-Functional               |
| ---------------------- | ---------------------------- |
| What the system does   | How well it works            |
| Defines features       | Defines quality              |
| Login, search, payment | Security, speed, reliability |
| Focuses on behavior    | Focuses on performance       |

**Important scenario:**

Consider a food delivery application.

- The user can place an order. → Functional
- The application loads within 2 seconds. → Non-functional
- The user can track delivery. → Functional
- Payment data must be encrypted. → Non-functional

**Exam trick**

If the statement describes an action or feature, think Functional.

If it describes speed, security, reliability, usability, or another quality, think Non-Functional.

### **Level 1: Business Level**

**Business Requirements**

**Definition:** Business requirements describe the high-level goals, objectives, and vision of an organization.

They explain WHY the organization wants to build a software system.

**Main focus:**

- Business goals
- Objectives
- Expected value
- Return on investment (ROI)
- Regulatory compliance

**Examples from your slides:**

1. Increase online course registration revenue by 25%.
2. Reduce patient waiting time by 30%.
3. Ensure 100% compliance with data protection regulations.

**Simple example:**

A university wants to improve student performance by introducing an academic management system.

Its business requirement could be:

"Increase student retention rates by 15% over two academic years."

Remember: Business Level = WHY build the system?

### **Level 2: User Level**

**User Requirements**

**Definition:** User requirements describe the tasks, goals, and activities that users must perform using the software.

They explain what users need from the system.

**Main focus:**

- User tasks
- User goals
- Use cases
- User stories

**Examples:**

- Student wants to view the semester timetable.
- Teacher wants to grade assignments online.
- Patient wants to book an appointment online.

**Simple example:**

A student wants to view semester results through a university portal.

Remember: User Level = WHAT can users do?

### **Level 3: Product Level**

**Product Requirements**

**Definition:** Product requirements describe the detailed functions, behavior, and constraints that must be included in the software.

They explain how the system should behave.

Multiple functional requirements may be needed to fulfill one user requirement.

**Example from your slides: Credit Card System**

User requirement:

"The customer should be able to swipe a credit card."

This requires multiple functional requirements:

1. System prompts the customer to insert the card.
2. System detects when the card is swiped.
3. System checks whether the card was read correctly.
4. System asks the customer to swipe again if the card is read incorrectly.
5. System reads the information from the magnetic strip.

Remember: Product Level = HOW the system behaves.

### **Comparison of all three levels**

| Level    | Main question       | Focus                        |
| -------- | ------------------- | ---------------------------- |
| Business | Why?                | Organization's goals         |
| User     | What can users do?  | User tasks                   |
| Product  | How does it behave? | Detailed system requirements |

**Memorize this table.** It is particularly useful for short questions, MCQs, and scenario-based questions.

## **5. Business Requirements vs Business Rules**

This is an important distinction from pages 9–10.

### **Business Requirements**

These describe what an organization wants to achieve.

Example:

"Increase student retention rates by 15% over two academic years."

### **Business Rules**

**Definition:** Business rules are policies, conditions, standards, or restrictions that exist independently of software.

They explain how an organization operates.

Example:

"A student whose CGPA falls below 2.00 at the end of a semester shall be placed on Academic Probation."

### **Difference**

| Business Requirement                 | Business Rule                             |
| ------------------------------------ | ----------------------------------------- |
| Defines organizational goals         | Defines organizational policies           |
| Explains what the organization wants | Explains what conditions must be followed |
| Focuses on objectives                | Focuses on rules                          |
| Example: Increase student retention  | CGPA below 2.00 means probation           |

**Understand with one example:**

A university wants to improve student performance.

- Goal: Increase student performance by 20%. → Business Requirement.
- Policy: Students below CGPA 2.00 are placed on probation. → Business Rule.

**Exam-ready definition:**

Business rules are policies, constraints, standards, or conditions that govern how an organization operates and exist independently of software.

## **7. Product Level Requirements**

Your slides explain four important product-level requirement categories on page 13.

### **1. External Interface Requirements**

These describe the information flow between the software and external systems, hardware, or users.

Example:

A university portal communicates with a payment gateway to process fee payments.

### **2. Constraints**

Constraints are restrictions on the choices available when designing and developing software.

Example:

The software must use no more than 50% of available system memory.

Other examples:

- Fixed budget.
- Required programming language.
- Limited development time.

### **3. Data Requirements**

These describe the specific data items or data structures that must be included in the software.

Example:

A payroll system must store:

- Employee ID.
- Employee name.
- Current salary.
- Year-to-date payroll data.

### **4. Product Requirements Document (PRD)**

**Definition:** A PRD is a document written by a company that defines the product being developed or the requirements for new features in an existing product.

It describes what the product should provide.

### **Quick revision**

| Term               | Remember                               |
| ------------------ | -------------------------------------- |
| External Interface | Communication with external systems    |
| Constraints        | Restrictions or limitations            |
| Data Requirements  | Data that must be stored or included   |
| PRD                | Document defining product requirements |

## **8. W2 – WHY (Problematic Requirements)**

Page 14 explains problems that can negatively affect software development projects.

Your slides mention six important issues.

### **1. Incomplete Requirements**

Some requirements are missing or not properly defined.

**Consequence:** The software may not meet all customer and user needs.

Example: A university portal is developed without including the assignment submission feature.

### **2. Lack of User Involvement**

Users are not properly involved in the requirements process.

**Consequence:** The system may not meet actual user needs.

Example: Developers create a student portal without asking students what features they need.

### **3. Requirements Churn**

**Definition:** Requirements churn means the constant addition, deletion, or modification of requirements after they have been officially agreed upon.

Example:

- First, the client requests a login feature.
- Later, the client adds biometric login.
- Then, the client changes the login process again.

This is requirements churn.

### **4. Wasted Resources**

Time, money, and effort are wasted because of poor or changing requirements.

Example: Developers build a feature that is later rejected.

### **5. Gold Plating**

Gold plating means adding extra features that were not requested or required by the customer.

Example:

The customer requests a simple student portal, but developers add unnecessary animations and extra features.

### **6. Inaccurate Estimates**

Incorrect estimates of project time, cost, or resources.

Example:

A project is estimated to take one month, but it actually takes three months.

### **Memorize all six**

**Six problematic requirements**

1. Incomplete requirements
2. Lack of user involvement
3. Requirements churn
4. Wasted resources
5. Gold plating
6. Inaccurate estimates

## **9. Kano Model**

Important exam topic

Your slides explain the Kano Model on pages 16–18.

**Definition:** The Kano Model was developed by Noritaki Kano. It explains the relationship between customer satisfaction and product quality requirements.

It helps us understand how different product features affect customer satisfaction.

The graph has two axes:

- X-axis: Company's execution, from not executed to executed very well.
- Y-axis: Customer satisfaction, from low to high.

### **Five categories of the Kano Model**

**1. Must-be Quality**

These are basic features that customers expect.

If they are missing, customers become dissatisfied.

Example: A banking application must allow secure login.

**2. One-dimensional / Performance Quality**

The better these features perform, the more satisfied customers become.

If performance is poor, customers become dissatisfied.

Example: Faster loading speed in a mobile application.

**3. Attractive Quality**

These are unexpected features that make customers happy when provided.

Their absence does not cause dissatisfaction.

Example: An unexpected AI study recommendation feature in a student application.

**4. Indifferent Quality**

These features do not affect customer satisfaction, whether they are present or absent.

Example: A decorative feature that users neither need nor care about.

**5. Reverse Quality**

These features have the opposite effect on customer satisfaction.

A feature may satisfy some users but make others dissatisfied.

Example: An optional interface feature that some users prefer, while others find it inconvenient.

### **Very important difference**

| Category        | Effect on satisfaction                 |
| --------------- | -------------------------------------- |
| Must-be         | Missing = dissatisfaction              |
| One-dimensional | Better performance = more satisfaction |
| Attractive      | Present = extra satisfaction           |
| Indifferent     | No significant effect                  |
| Reverse         | Can reduce satisfaction                |

### **Expected, Basic and Exciting Quality**

Your page 18 also explains three quality ideas.

- **Expected Quality:** Features that customers explicitly request.
- **Basic Quality:** Features that customers expect as a minimum. Their absence causes dissatisfaction.
- **Exciting Quality:** Unexpected and innovative features that make customers happy.

**Important exam point:** Basic and exciting requirements can easily be missed if requirements engineers do not properly involve stakeholders or perform detailed elicitation and analysis.

## **11. W4 – WHEN**

Your slide on page 23 divides requirements work into two important activities.

### **A. Requirements Development**

Requirements development includes:

- Identifying requirements.
- Capturing requirements.
- Agreeing upon requirements.
- Defining and integrating business, user, and product-level requirements.

Most activities occur early, but further details can be added later.

### **B. Requirements Management**

Requirements management includes:

- Requesting changes to baselined requirements.
- Performing impact analysis.
- Approving or rejecting changes.
- Implementing approved changes.

### **Difference between Requirements Development and Management**

| Requirements Development | Requirements Management     |
| ------------------------ | --------------------------- |
| Identifies requirements  | Manages requirements        |
| Captures requirements    | Handles changes             |
| Defines requirements     | Performs impact analysis    |
| Agrees on requirements   | Approves or rejects changes |

**Remember:**

Development = Discover and define requirements.

Management = Control and manage requirement changes.

## **12. H – HOW**

Your page 24 explains that Software Requirements Engineering is a disciplined, process-oriented approach to the definition, documentation, and maintenance of software requirements throughout the Software Development Life Cycle.

### **Important points**

1. Requirements development is an iterative process.
2. Requirements are not developed in only one attempt.
3. Requirements are refined and improved over time.
4. Requirements must be documented and maintained.

**What does iterative mean?**

Iterative means repeating activities to improve the result.

For example:

- First, collect requirements.
- Then, analyze them.
- Identify missing information.
- Improve the requirements.
- Repeat until they are clear and acceptable.

**Exam-ready definition**

Software Requirements Engineering is a disciplined, process-oriented approach to defining, documenting, and maintaining software requirements throughout the Software Development Life Cycle.
